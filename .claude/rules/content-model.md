# Content Model

Editor-managed content lives in `src/content/`, authored through the Keystatic admin UI at `/keystatic` (`src/pages/keystatic/`) and read by Astro through the collections in `src/content.config.ts`.

- **Programs are single-source: the `programs` collection is the only place a program is defined.** `src/lib/programs.ts` (`getPrograms`/`getProgramsByPintu`/`getProgramPages`) reads it and every consumer derives from that: homepage cards (`ProgramHighlights`, list and order chosen by the `home` singleton), mega-menu (`Header` groups by `PINTU`), calculator select (`DonationCalculator`, pintu `food` only, since the per-pax price is uniform), the pintu landing pages, jejak validation, the dynamic detail route, and OG images. A program's `pintu` places it in a mega-menu column and on that pintu's landing page; `active` + a filled `detail.description` means it gets its own page (see the route note in `routing-taxonomy.md`). This replaced an earlier split where the same program was hand-duplicated across `MAKANAN_PROGRAMS`, `PROGRAM_MENU`, the collection, and a hardcoded `.astro`, none of which exist anymore.
- `src/content/` holds the editor-managed content, all of it editable via the Keystatic admin UI at `/keystatic` (`src/pages/keystatic/`). Astro reads it through the collections in `src/content.config.ts`; Keystatic writes it through `keystatic.config.ts`. **The two configs must agree on file extension** — Keystatic derives it from `format`, so a mismatch makes the admin UI silently list zero entries while the site keeps rendering fine (this happened: `format: { data: 'yaml' }` looks for `*.yaml`, but the files were `*.md`).
  - `programs` — one `*.yaml` per program, a Keystatic collection (`slugField: label` → filename is the clean slug, e.g. `jumat-berkah.yaml`, which is also the detail-page route). Fields: `label`, `pintu` (one of `PINTU_IDS`), `order` (sort within its pintu), `active`, `image` (the program's cover — read through `getProgramCover()` in `programs.ts`, which is the only answer to "what does this program look like": every surface that shows the program uses it, i.e. the home hero donation card, the program page hero, the parked highlights card, and the CTA at the bottom of a jejak. **A cover is the program's own asset, never a frame borrowed from its jejak documentation** — a chain that fell back to "newest jejak cover" was tried and removed, since "newest" is a date order rather than a choice, so it promoted a ceremonial group photo to be the face of the program and changed that face again on every new jejak. Empty falls straight through to `program-promo.png`), `summary` (card+menu text), and a `detail` object (eyebrow/description/features) filled only for active programs that get a page. Ordering is an explicit `order` field, not a filename prefix — the entry still needs individual routing so it can't be an array-singleton like `faq`/`footer`. The same entry also carries a `stage` object (kicker/lead/status/caption/ctaLabel/ctaWhatsapp/ctaMessage) holding that program's slide copy in the homepage `ProgramStage.astro` band. Everything in `stage` is optional with a default, so the inactive program entries stay valid untouched, and `lead` empty falls back to `summary` so the mega-menu text is never dragged along by a slide edit. `status` has no switch of its own: the component shows it only while the program has no cover, which is the same test that decides the grey dormant treatment and pushes that slide to the back of the band, so an undocumented program can never be dressed up as a documented one from the CMS.
  - `jejak` holds one `*.mdoc` per kegiatan, a Keystatic collection using Markdoc because each entry carries a narrative body; `slugField: title` with the convention `<program-slug>-YYYY-MM-DD`, editors type this into the slug box themselves — it isn't derived automatically from the title, which is free text. **Two jejak for the same program on the same date collide on that convention** (e.g. two separate Jumat Berkah activities both landing on 2026-07-31): append a short kawasan slug to disambiguate, `<program-slug>-YYYY-MM-DD-<kawasan>` (e.g. `jumat-berkah-2026-07-31-bogor` and `jumat-berkah-2026-07-31-dukuh-atas`), rather than merging both activities' numbers into one entry — this happened once and produced metrics that summed two unrelated events under one misleading title, and dropped that entry's `organisasi` attribution in the process. Fields: `title`, `program` (a `fields.relationship` into `programs`), `organisasi` (optional `fields.relationship` into the `organisasi` collection, lateral to `program` — see the routing note in `routing-taxonomy.md`), `date`, `location`, `summary`, `metrics` (label+value pairs, summed by label when aggregated), `cover`/`gallery` (each an object of `image` + optional `alt` + optional `caption`, not a bare path — see the photo pipeline note in `image-pipeline.md`. Both text fields may be left empty on purpose: a gallery runs to a dozen photos and demanding alt on each one buys typed-anything rather than description, so an empty alt falls back to a title-derived sentence in `jejak.ts` and an empty caption simply renders nothing. `caption` is the one an editor should reach for first — it is what a visitor reads under the enlarged photo, and unlike alt it has no automatic stand-in), `reportPdf` (optional `fields.file`, manual upload to `public/uploads/jejak-reports/`, no auto-generation — rendered as a download link on the jejak detail page when present, section omitted when empty), and `published`. `src/lib/jejak.ts` is the only reader: it drops unpublished entries and orphans whose `program` no longer resolves, so deleting or renaming a program cannot leave a dangling page or a dangling impact number. An orphaned `organisasi` reference (deleted/deactivated) is treated more leniently: the jejak itself still renders and aggregates normally under its program/pintu, it's just excluded from that organisasi's own aggregation (`getJejakByOrganisasi` in `jejak.ts`) — organisasi is an optional add-on, not a validity requirement.
  - `organisasi` — one `*.yaml` per institutional donor (community or company that gives routinely), a Keystatic collection (`slugField: label`, same pattern as `programs`). Fields: `label`, `logo` (optional `fields.image`, uploaded to `public/uploads/organisasi` and served as a plain `<img>` — deliberately not routed through `astro:assets` like jejak/program photos, since it's a small logo), `summary`, `detail` (`description`, `since`, optional `instagram`/`website`), and `active`. Same publish gate as `programs`: `active` + `detail.description` filled = gets `/organisasi/<slug>/`. Deliberately one schema with no community/company subtype — the data shape is identical, only the narrative in `detail.description` differs (see `design.md` in the `add-food-programs-organisasi` change for the rejected alternatives). `src/lib/organisasi.ts` (`getOrganisasi`/`getOrganisasiPages`) is the single-source reader, mirroring `programs.ts`.
  - `faq`, `footer` — `*.json` singletons holding an **array** of items rather than one file per entry. Ordering is the array's own order, which Keystatic exposes as drag-and-drop; they were collections until the ordering turned out to depend on filename prefixes (`01-`, `02-`) that Keystatic doesn't reproduce — it derives filenames from `slugField`, so an entry added through the admin sorted into an arbitrary position. Anything whose display order matters and whose entry count stays small belongs here rather than in a collection.
  - `settings`, `about`, `seo` — `*.json` singletons.
  - `home` — `*.json` singleton holding *placement*, not content: which programs the homepage "Program Aktif" section highlights, in what order, plus that section's eyebrow/title. `src/lib/home.ts` (`getProgramSection`) joins the stored slugs back onto the `programs` collection, so a highlighted program is never duplicated here. Because the list stores slugs, the join must stay defensive: a deleted or renamed program leaves a dangling slug that Keystatic will not flag, so `getProgramSection` drops unknown/empty slugs and duplicates, and `ProgramHighlights` renders nothing when the resolved list is empty. The card photo stays on the program entry (`image`, uploaded to `src/assets/programs/`) since it belongs to the program, not to the slot. `home` also holds `programStage` (kicker/title/lead/statement): the first slide of `ProgramStage.astro` carries the section's own narrative rather than any one program's, so that copy belongs to the homepage; `statement` stores only the tail of the closing sentence because the component prints the leading program's own label in front of it.
  - Share-image fields (`seo.pages[].image`, and the SEO blocks on `about`/`legal`) are `fields.image` — Keystatic uploads to `public/uploads/share` and **writes `null` when the field is cleared**, so their zod schema must be `.nullish()` (not `.optional()`) and downstream types `string | null`, or a cleared image fails validation. Default/logo paths that point at fixed root assets stay `fields.text` on purpose.
  - `seo` holds every search/share-facing string: site name, defaults, the Organization node, and a `pages[]` array keyed by route path. Two consumers read it and must stay in sync — `BaseLayout.astro` (meta tags + JSON-LD `@graph`) and `pages/open-graph/[...route].ts` (the generated share images) — so a title edited in Keystatic changes both. Resolution order per page is explicit prop → matching `pages[]` entry → default; legal pages pass props because their titles come from the `legal` singleton instead.
  - `legal` (privacy/terms/transparency, rendered by `privasi/syarat/transparansi.astro`) — long-form prose, so `*.mdoc` (Markdoc) via `@astrojs/markdoc`; Keystatic's `contentField` only supports `.mdoc`. Modelled as three **singletons**, not a collection, because each has a hard-coded route calling `getEntry` with a fixed id — a collection's add/delete/rename-slug affordances would break those routes.
- `src/lib/format.ts` holds pure functions (Rupiah formatting, metric formatting, WhatsApp link and message building) used by both server-rendered markup and the client-side calculator script. It and `aggregateMetrics` in `impact.ts` are the only unit-tested parts (`bun test`); `impact.ts` imports `jejak.ts` lazily inside its async functions exactly so the pure aggregator stays testable without pulling in `astro:content`, which only exists inside the Astro runtime.
