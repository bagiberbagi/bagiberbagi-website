# Routing & Taxonomy

- `src/pages/index.astro` assembles the beranda from one component per section (`Hero` + `Stats` sharing one photo zone, then `ProgramFeatures`, `ProgramHighlights`, `HowItWorks`, `ImpactSection`, `FaqHome`, `JoinUs`, `PintuSection`). `JejakTerbaru.astro` is finished and wired but its import is commented out on purpose: the showcase lives at `/jejak/` until the home design catches up.
- `src/consts.ts` holds small structured UI data as plain typed arrays/objects: `FEATURES`, `STEPS`, `IMPACTS`, `NAV_LINKS`, `PINTU_IDS`/`PINTU`/`PINTU_LABEL`, `CATEGORY_CONTENT`, plus the `IconName` and `ProgramMenuCategoryData` types. Deliberately not a Content Collection, since these are fixed-size, tightly coupled to one section each, and never individually routed. Editor-managed prose/data lives in `src/content/` instead (see `content-model.md`).
  - `NAV_LINKS` is four items (Pintu Berbagi, Jejak & Dampak, Tentang Kami, FAQ), ordered along the donor's trust path. No "Home" because the logo is the way back, and no "Cara Kerja" because the version that actually helps differs per program, so it lives on the program page with a secondary link from the Hero. The `program` entry renders as the mega-menu trigger, not a link, so its `href` is only a fallback.
  - **`PINTU_IDS` is the single source of the pintu taxonomy.** `PintuId`, the zod enum in `content.config.ts`, and the Keystatic select options all derive from it, so adding or removing a pintu is a `consts.ts`-only edit. Each `PINTU` entry also carries its identity color trio (`color`/`colorTint`/`colorDeep`), fed to markup as the `--cat` CSS var, so no consumer hardcodes a pintu color.
  - `CATEGORY_CONTENT` is the conceptual copy for the pintu landing pages (stats, contribute, how-it-works, FAQ, CTA), still hardcoded and a candidate to move into Keystatic. Every block is optional and an empty one is not rendered, so only `food` is filled and the other four pintu pages render lean but tidy.
- Routes live in `src/pages/` under an "entity = pintu (kategori) → program → jejak" information architecture. **Pintu is a category/filter, not a page-owning entity** (there is no `/berbagi/` hub and no nested `/berbagi/<pintu>/...` route): pintu surfaces via home `PintuSection`, the mega-menu, colored badges, and the `?berbagi=<pintu-slug>` filter on `/jejak/`. Pages: `index`; `faq`; `tentang`; **program detail** `program/[program].astro` (`/program/<slug>/`, dynamic from `getProgramPages()`, so activating a program in Keystatic + filling its `detail` generates the page with no new file; bare `/program` redirects to `/#pintu` via `astro.config`; on a static build that redirect ships as a noindex meta-refresh stub, not an HTTP 30x, which is why programme pages must declare `breadcrumbTrail` rather than let the crumb be derived from the URL — the derived one names `/program/` and that page does not really exist); **pintu landing** `berbagi-[pintu].astro` (flat `/berbagi-<pintu>/`, one per `PINTU`, a thin channel page carrying concept/story + SEO + its program list + roadmap status, but NOT "cara kerja", which lives on the program because it varies per program); the **Jejak & Dampak showcase** `jejak/index.astro` and **jejak detail** `jejak/[slug].astro` (tier `article`, with `Share.astro` + `Lightbox.astro`); **organisasi directory** `organisasi/index.astro` (`/organisasi/`) and **organisasi detail** `organisasi/[slug].astro` (`/organisasi/<slug>/`, dynamic from `getOrganisasiPages()`); the legal pages (`privasi`, `syarat`, `transparansi`); Keystatic admin (`keystatic/`); and the build-time share images `open-graph/[...route].ts` (manual entries plus one per program page, one per organisasi page, and one per jejak, the latter two namespaced `organisasi/<slug>` / `jejak/<slug>` so slugs across programs, organisasi, and jejak can never collide). "Dampak" is not an entity but a computed lens over the `jejak` collection (`src/lib/impact.ts`: `getGlobalImpact`/`getPintuImpact`/`getProgramImpact`, sum-by-label via `aggregateMetrics`); `src/lib/jejak.ts` is the single-source reader for jejak. Mega-menu via `ProgramMenuCategory.astro` + `program-menu.js`.
- **`organisasi` is a lateral entity, not part of the pintu → program → jejak hierarchy.** It represents institutional donors (communities/companies) that give routinely, attached to `jejak` via an optional `jejak.organisasi` relationship that stands independent of `jejak.program` — one organisasi's jejak can span multiple programs (e.g. one under Community Giving, another under Ramadhan Berbagi), and `getOrganisasiImpact` (`impact.ts`) sums metrics across all of them into a single dashboard. `src/lib/organisasi.ts` (`getOrganisasi`/`getOrganisasiPages`) is the single-source reader, mirroring `programs.ts`'s pattern; publish gate is the same as programs (`active` + `detail.description` filled = gets `/organisasi/<slug>/`). `getJejakByOrganisasi` (`jejak.ts`) excludes jejak whose organisasi has been deleted or deactivated from that organisasi's aggregation and history list — but such a jejak still renders and aggregates normally under its `program`/pintu, since organisasi is an optional add-on, not a validity requirement (unlike an orphaned `program` reference, which drops the whole jejak). Not surfaced in the mega-menu or pintu pages — reachable only via `/organisasi/` and any cross-links a page chooses to add.
- **`/jejak/` shapes its feed by how many jejak exist**, so no card is ever left orphaned: 1 renders a single wide card, 2 render two equal cards side by side (throwing the second into a 3-column grid makes it look stranded), 3 to 6 render a wide "terbaru" card plus a compact grid of the rest, and 7 or more switch to archive mode, a uniform grid grouped by month with no featured card at all (month headings already convey recency, and a lone wide card mid-archive breaks the rhythm; the heading is dropped entirely when every jejak falls in one month). All shapes are the same `JejakCard.astro` under `variant="wide" | "stack" | "compact"`, with `titleLevel` dropping to 4 beneath a month heading so the h2 → h3 → h4 order never skips. The inline script owns two filters at once: the pintu chips, and a reveal window of 9 cards (`FEED_REVEAL_STEP`, handed to the DOM via `data-jstep` so the number lives in one place). The window is counted over cards that pass the chip, so switching pintu resets it. Every card is rendered server-side and only its visibility is toggled, which keeps the feed whole for crawlers and for JS-off visitors; for the same reason the "tampilkan lebih banyak" button ships `hidden` and is revealed by the script, since without JS nothing is limited and the button would be a lie.
