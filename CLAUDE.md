# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Landing page situs donasi bagiberbagi.id (komunitas penyalur bantuan makanan & dukungan UMKM). Astro static site, bun as package manager/test runner.

## Commands

- `bun install` — install dependencies
- `bun run dev` — dev server (http://localhost:4321)
- `bun run build` — build static site to `dist/`
- `bun run preview` — preview the production build
- `bun test` — run unit tests (`src/lib/*.test.ts`, yaitu `format` + `impact`)
- `bunx astro check` — type-check `.astro` files

## Architecture

Astro static site (`output: 'static'`, no adapter), Tailwind CSS, TypeScript strict. Deploys to a self-managed VPS (nginx + certbot, see `deploy/README.md`) via GitHub Actions on push to `main`.

- `src/pages/index.astro` assembles the beranda from one component per section (`Hero` + `Stats` sharing one photo zone, then `ProgramFeatures`, `ProgramHighlights`, `HowItWorks`, `ImpactSection`, `FaqHome`, `JoinUs`, `PintuSection`). `JejakTerbaru.astro` is finished and wired but its import is commented out on purpose: the showcase lives at `/jejak/` until the home design catches up.
- `src/consts.ts` holds small structured UI data as plain typed arrays/objects: `FEATURES`, `STEPS`, `IMPACTS`, `NAV_LINKS`, `PINTU_IDS`/`PINTU`/`PINTU_LABEL`, `CATEGORY_CONTENT`, plus the `IconName` and `ProgramMenuCategoryData` types. Deliberately not a Content Collection, since these are fixed-size, tightly coupled to one section each, and never individually routed. Editor-managed prose/data lives in `src/content/` instead.
  - `NAV_LINKS` is four items (Pintu Berbagi, Jejak & Dampak, Tentang Kami, FAQ), ordered along the donor's trust path. No "Home" because the logo is the way back, and no "Cara Kerja" because the version that actually helps differs per program, so it lives on the program page with a secondary link from the Hero. The `program` entry renders as the mega-menu trigger, not a link, so its `href` is only a fallback.
  - **`PINTU_IDS` is the single source of the pintu taxonomy.** `PintuId`, the zod enum in `content.config.ts`, and the Keystatic select options all derive from it, so adding or removing a pintu is a `consts.ts`-only edit. Each `PINTU` entry also carries its identity color trio (`color`/`colorTint`/`colorDeep`), fed to markup as the `--cat` CSS var, so no consumer hardcodes a pintu color.
  - `CATEGORY_CONTENT` is the conceptual copy for the pintu landing pages (stats, contribute, how-it-works, FAQ, CTA), still hardcoded and a candidate to move into Keystatic. Every block is optional and an empty one is not rendered, so only `food` is filled and the other four pintu pages render lean but tidy.
- **Programs are single-source: the `programs` collection is the only place a program is defined.** `src/lib/programs.ts` (`getPrograms`/`getProgramsByPintu`/`getProgramPages`) reads it and every consumer derives from that: homepage cards (`ProgramHighlights`, list and order chosen by the `home` singleton), mega-menu (`Header` groups by `PINTU`), calculator select (`DonationCalculator`, pintu `food` only, since the per-pax price is uniform), the pintu landing pages, jejak validation, the dynamic detail route, and OG images. A program's `pintu` places it in a mega-menu column and on that pintu's landing page; `active` + a filled `detail.description` means it gets its own page (see route note below). This replaced an earlier split where the same program was hand-duplicated across `MAKANAN_PROGRAMS`, `PROGRAM_MENU`, the collection, and a hardcoded `.astro`, none of which exist anymore.
- `src/content/` holds the editor-managed content, all of it editable via the Keystatic admin UI at `/keystatic` (`src/pages/keystatic/`). Astro reads it through the collections in `src/content.config.ts`; Keystatic writes it through `keystatic.config.ts`. **The two configs must agree on file extension** — Keystatic derives it from `format`, so a mismatch makes the admin UI silently list zero entries while the site keeps rendering fine (this happened: `format: { data: 'yaml' }` looks for `*.yaml`, but the files were `*.md`).
  - `programs` — one `*.yaml` per program, a Keystatic collection (`slugField: label` → filename is the clean slug, e.g. `jumat-berkah.yaml`, which is also the detail-page route). Fields: `label`, `pintu` (one of `PINTU_IDS`), `order` (sort within its pintu), `active`, `image` (homepage card photo), `summary` (card+menu text), and a `detail` object (eyebrow/description/features) filled only for active programs that get a page. Ordering is an explicit `order` field, not a filename prefix — the entry still needs individual routing so it can't be an array-singleton like `faq`/`footer`.
  - `jejak` holds one `*.mdoc` per kegiatan, a Keystatic collection using Markdoc because each entry carries a narrative body; `slugField: title` with the convention `<program-slug>-YYYY-MM-DD`. Fields: `title`, `program` (a `fields.relationship` into `programs`), `date`, `location`, `summary`, `metrics` (label+value pairs, summed by label when aggregated), `cover`/`gallery` (see the photo pipeline note below), and `published`. `src/lib/jejak.ts` is the only reader: it drops unpublished entries and orphans whose `program` no longer resolves, so deleting or renaming a program cannot leave a dangling page or a dangling impact number.
  - `faq`, `footer` — `*.json` singletons holding an **array** of items rather than one file per entry. Ordering is the array's own order, which Keystatic exposes as drag-and-drop; they were collections until the ordering turned out to depend on filename prefixes (`01-`, `02-`) that Keystatic doesn't reproduce — it derives filenames from `slugField`, so an entry added through the admin sorted into an arbitrary position. Anything whose display order matters and whose entry count stays small belongs here rather than in a collection.
  - `settings`, `about`, `seo` — `*.json` singletons.
  - `home` — `*.json` singleton holding *placement*, not content: which programs the homepage "Program Aktif" section highlights, in what order, plus that section's eyebrow/title. `src/lib/home.ts` (`getProgramSection`) joins the stored slugs back onto the `programs` collection, so a highlighted program is never duplicated here. Because the list stores slugs, the join must stay defensive: a deleted or renamed program leaves a dangling slug that Keystatic will not flag, so `getProgramSection` drops unknown/empty slugs and duplicates, and `ProgramHighlights` renders nothing when the resolved list is empty. The card photo stays on the program entry (`image`, uploaded to `public/uploads/programs`) since it belongs to the program, not to the slot.
  - Share-image fields (`seo.pages[].image`, and the SEO blocks on `about`/`legal`) are `fields.image` — Keystatic uploads to `public/uploads/share` and **writes `null` when the field is cleared**, so their zod schema must be `.nullish()` (not `.optional()`) and downstream types `string | null`, or a cleared image fails validation. Default/logo paths that point at fixed root assets stay `fields.text` on purpose.
  - `seo` holds every search/share-facing string: site name, defaults, the Organization node, and a `pages[]` array keyed by route path. Two consumers read it and must stay in sync — `BaseLayout.astro` (meta tags + JSON-LD `@graph`) and `pages/open-graph/[...route].ts` (the generated share images) — so a title edited in Keystatic changes both. Resolution order per page is explicit prop → matching `pages[]` entry → default; legal pages pass props because their titles come from the `legal` singleton instead.
  - `legal` (privacy/terms/transparency, rendered by `privasi/syarat/transparansi.astro`) — long-form prose, so `*.mdoc` (Markdoc) via `@astrojs/markdoc`; Keystatic's `contentField` only supports `.mdoc`. Modelled as three **singletons**, not a collection, because each has a hard-coded route calling `getEntry` with a fixed id — a collection's add/delete/rename-slug affordances would break those routes.
  - `analytics` — a `*.json` singleton switchboard: per-provider `{enabled, id}` (PostHog, Umami, GA4, Meta Pixel, Clarity, GTM) + a `consentBanner` toggle. `src/lib/analytics.ts` (`getAnalytics`) resolves it to per-provider `active` (enabled **and** id non-empty) plus flags (`anyCookieProvider`, `needsConsentBanner`, `misconfigured` → build-time `console.warn`). `Analytics.astro` (mounted in `BaseLayout` `<head>`) injects each provider's script **only when active**, all as `is:inline` so the gating actually holds (bundled `<script>` can't be conditional); default all-off ⇒ zero analytics scripts. Cookie providers are consent-gated (Google via Consent Mode v2 default-denied; Pixel/Clarity deferred until the `bb:consent-granted` event from `ConsentBanner.astro`); PostHog and Umami run cookieless. Interaction tracking is an inline event layer that fans one event out to PostHog + `dataLayer`, driven by `data-track` / `data-track-*` attributes on elements (WA "Donasi" click = the conversion). Provider IDs are public client-side keys, safe in the repo. See `openspec/changes/add-analytics-tooling/`.
- **Lebar konten punya satu sumber: `src/components/Container.astro`.** Kosakata tier: `full` (tanpa max-w & tanpa padding, buat band foto/warna edge-to-edge), `wide` 1280 (default beranda), `standard` 1024 (default halaman non-beranda), `article` 768 (halaman baca bergambar, mis. jejak detail: foto, carousel, grid metrik, dan teks berbagi satu kolom), `prose` 672 (teks dibaca), `form` 448 (panel input). Semua tier kecuali `full` bawa `mx-auto` + padding horizontal `px-5 md:px-10`, jadi `.section` di `global.css` cuma mengatur ritme vertikal. Lebar per halaman itu default, bukan kunci: satu seksi boleh menyimpang demi estetikanya (mis. `ProgramHighlights` pakai `wide` saat grid dan `standard` saat kartu tunggal), asal menyimpangnya ke tier bernama, bukan bikin `max-w-*` mentah baru. Nilai tier hidup di `@theme` (`--container-*`) pada `src/styles/global.css`, bukan di `tailwind.config.mjs`. Untuk markup yang terlalu dalam buat dibungkus komponen (pil navbar, panel mega-menu, `ConsentBanner`, panel `DonationCalculator`) pakai token util langsung: `max-w-wide` / `max-w-standard` / `max-w-article` / `max-w-text` / `max-w-form`. Tier `prose` sengaja bernama `max-w-text` di util karena `max-w-prose` sudah dikunci Tailwind v4 ke 65ch dan tak bisa ditimpa lewat tema. Sisa `max-w-*` mentah yang masih ada semuanya ukuran lokal di dalam kartu/kolom (mis. `max-w-md` pada paragraf kartu), bukan shell halaman.
- `src/lib/format.ts` holds pure functions (Rupiah formatting, metric formatting, WhatsApp link and message building) used by both server-rendered markup and the client-side calculator script. It and `aggregateMetrics` in `impact.ts` are the only unit-tested parts (`bun test`); `impact.ts` imports `jejak.ts` lazily inside its async functions exactly so the pure aggregator stays testable without pulling in `astro:content`, which only exists inside the Astro runtime.
- `src/scripts/*.js` are small vanilla-JS modules (no UI framework) each imported via a `<script>` tag in the one component that owns that behavior: mobile nav, header scroll state, program mega-menu, hero countdown, stats count-up, donation calculator, FAQ accordion (shared by `Faq` and `FaqHome`), fade-in-on-scroll, jejak gallery lightbox, share buttons, legal-page TOC scrollspy. The `/jejak/` feed script is the one exception, inline in the page because it is coupled to that page's markup contract.
- Design mockups are **git-ignored, local-only** references (see `.gitignore`), all flat under `mockup/`: `*.dc.html` site-builder exports plus their shared runtime (`image-slot.js`, `support.js`, `content.js`). Workflow: a `.dc.html` export is dropped in as the visual/content reference for building a page, then used as the spec — never imported or deployed. Map its raw hex to the design-system tokens (don't copy mockup colors verbatim), and treat its `sc-for`/`{{ }}` template placeholders as dynamic slots (real content lives in the Astro content collections, not the mockup). Files stay on disk for iteration and are deleted manually once spent.
- Routes live in `src/pages/` under an "entity = pintu (kategori) → program → jejak" information architecture. **Pintu is a category/filter, not a page-owning entity** (there is no `/berbagi/` hub and no nested `/berbagi/<pintu>/...` route): pintu surfaces via home `PintuSection`, the mega-menu, colored badges, and the `?berbagi=<pintu-slug>` filter on `/jejak/`. Pages: `index`; `faq`; `tentang`; **program detail** `program/[program].astro` (`/program/<slug>/`, dynamic from `getProgramPages()`, so activating a program in Keystatic + filling its `detail` generates the page with no new file; bare `/program` redirects to `/#program` via `astro.config`); **pintu landing** `berbagi-[pintu].astro` (flat `/berbagi-<pintu>/`, one per `PINTU`, a thin channel page carrying concept/story + SEO + its program list + roadmap status, but NOT "cara kerja", which lives on the program because it varies per program); the **Jejak & Dampak showcase** `jejak/index.astro` and **jejak detail** `jejak/[slug].astro` (tier `article`, with `Share.astro` + `Lightbox.astro`); the legal pages (`privasi`, `syarat`, `transparansi`); Keystatic admin (`keystatic/`); and the build-time share images `open-graph/[...route].ts` (manual entries plus one per program page and one per jejak, the latter namespaced `jejak/<slug>` so a jejak slug can never collide with a program slug). "Dampak" is not an entity but a computed lens over the `jejak` collection (`src/lib/impact.ts`: `getGlobalImpact`/`getPintuImpact`/`getProgramImpact`, sum-by-label via `aggregateMetrics`); `src/lib/jejak.ts` is the single-source reader for jejak. Mega-menu via `ProgramMenuCategory.astro` + `program-menu.js`.
- **`/jejak/` shapes its feed by how many jejak exist**, so no card is ever left orphaned: 1 renders a single wide card, 2 render two equal cards side by side (throwing the second into a 3-column grid makes it look stranded), 3 to 6 render a wide "terbaru" card plus a compact grid of the rest, and 7 or more switch to archive mode, a uniform grid grouped by month with no featured card at all (month headings already convey recency, and a lone wide card mid-archive breaks the rhythm; the heading is dropped entirely when every jejak falls in one month). All shapes are the same `JejakCard.astro` under `variant="wide" | "stack" | "compact"`, with `titleLevel` dropping to 4 beneath a month heading so the h2 → h3 → h4 order never skips. The inline script owns two filters at once: the pintu chips, and a reveal window of 9 cards (`FEED_REVEAL_STEP`, handed to the DOM via `data-jstep` so the number lives in one place). The window is counted over cards that pass the chip, so switching pintu resets it. Every card is rendered server-side and only its visibility is toggled, which keeps the feed whole for crawlers and for JS-off visitors; for the same reason the "tampilkan lebih banyak" button ships `hidden` and is revealed by the script, since without JS nothing is limited and the button would be a lie.
- **Jejak photos live in `src/assets/jejak/`, not `public/uploads/`.** Only files under `src/` go through `astro:assets` (webp conversion, multiple widths, intrinsic dimensions for `<Image>`), and raw field photos run one to two megabytes each, which would sink `/jejak/` as documentation accumulates. Keystatic uploads there with `publicPath: '/src/assets/jejak/'`, matching exactly the key shape of the eager `import.meta.glob` in `src/lib/jejak.ts` that maps the stored string back to an image module; change one side without the other and every photo resolves to null. A missing file warns at build and falls back to a pintu icon rather than failing the build, because one stale path should not take the whole site down. **Deduplicating those modules must use object identity, never a property read like `img.src`**: Astro proxies image modules and marks the source file as "used directly" the moment any property is read outside the image pipeline, which copies the raw PNG into `dist/` and throws away the entire optimization. Cheap check after a build: `find dist/_astro dist/uploads -iname '*.png' | wc -l` must print 0. The `/jejak/` gallery also pre-builds a separate large webp per photo with `getImage()` for the lightbox, so opening one never fetches a thumbnail's multi-megabyte source. Program card photos are the deliberate exception, still `public/uploads/programs` served as a plain `<img>`.

## Git conventions

- One logical concern per commit, Conventional Commits style subject (`fix: ...`, `feat: ...`), body explains *why* when non-obvious.
- Never amend/force-push shared history.
- Code changes go through a feature branch, merged into `main` when they're verified — `main` is what deploys, so never commit code straight onto it. Docs-only edits may go direct.
- Push once a commit/feature is solid, not every intermediate step.
- No SemVer tagging yet.
- No PR review requirement (solo project) — revisit if a second contributor joins.
